# Decisões

Registro curto do que foi decidido e por quê. Entrada nova no fim. Decisão trocada não é
apagada: marque "**substituída por** <data>".

| Data | Decisão | Motivo |
|---|---|---|
| — | SHA-1 do conteúdo é o `_id` da imagem | duplicata impossível por construção; o hash sai enquanto o arquivo é gravado |
| — | O arquivo original nunca é alterado | o INI dos equipamentos é assinado |
| — | Imagem criptografada é aberta no upload e guardada aberta | hash, duplicata e INI funcionam igual para todas |
| — | A `Assinatura` do INI não vai para o banco | só faz sentido junto do arquivo original |
| — | Sem login: `X-User` (**substituída por** 2026-11-24) | rede interna; login próprio fica para depois |
| — | Perfis de import como dados (JSON no Mongo) | formato novo de CSV é configuração, não código |
| — | Caixas por **tarefa** (projeto do CVAT); import na página da tarefa casando com o banco todo; label desconhecida entra na tarefa | vários projetos (placa, letras, capacete) nas mesmas imagens |
| — | Export escolhe uma tarefa; "negativas" é opção (padrão: não) | o dataset é de um projeto só (**substituída por** 2026-11: várias tarefas) |
| — | Export Pascal VOC e layout por pastas (níveis de metadados com nomes por valor), além do train/valid/test | o dataset antigo da equipe é organizado por tipo/resolução/placa/direção/período |
| — | Modelo de nome de saída configurável no export (v2, padrão antigo, personalizado; precisa ter `{sha1}` ou `{name}`) | cada treino pede um nome |
| 2026-11 | Microsserviços **não**; **monólito modular** | o problema era organização, não escala; um binário é mais simples de manter |
| 2026-11 | Reorganizar módulo por módulo com a API sem mudar (`catalog`, `boxes`, `images`, `imports`, `exports`; o `store` sumiu) | dá para testar e fazer commit a cada passo |
| 2026-11 | Perfil de anotação configurável: campos da imagem + tipos de objeto, com ou sem caixa | projetos diferentes (capacete, eixo, pessoa) com campos diferentes |
| 2026-11 | O perfil é do **pacote** (padrão `veiculos`); troca só sem imagens verificadas | o fluxo é pacote → upload → fila; as verificadas foram conferidas no perfil atual |
| 2026-11 | **Tudo configurável** (os campos de veículo viram o perfil `veiculos`), trocado de uma vez, com migração na subida | um só jeito de anotar; sem código duplicado temporário |
| 2026-11 | Um campo `ref` se chama `equipment` ou `camera` | a cascata de renomear procura o campo pelo nome em qualquer perfil |
| 2026-11 | Valores de fora (CSV, INI, nome v2) passam pelo `Fit`: o que o perfil não tem fica de fora e vira aviso | um valor ruim não derruba o import |
| 2026-11 | Perfil em uso por um pacote não pode ser apagado | a anotação do pacote ficaria sem perfil |
| 2026-11 | **No disco toda imagem é `<sha1>.ext`**; o nome v2 é só um dado no banco; o export escolhe o nome | nenhum perfil precisa saber montar nome de arquivo; o caminho nunca muda |
| 2026-11 | Contexto para IAs em `contexto/`, com ponteiros por ferramenta na raiz | a equipe usa várias IAs e elas precisam seguir as mesmas regras |
| 2026-11 | O perfil de import diz qual perfil de anotação preenche (`annotation_profile`) e é validado contra ele; `vehicles` vira `objects.vehicle` (com `key: plate`) | os destinos de um CSV dependem do que o pacote anota |
| 2026-11 | Perfil de import num pacote de outro perfil de anotação **não é recusado**: o `Transform` usa o perfil do pacote e o resto vai para `outside_profile` | segue a regra do `Fit` (um valor de fora não derruba o import) |
| 2026-11 | O perfil de export tem `annotation_profile` só para os campos de filtros, pastas e nome; **não limita os pacotes** | os padrões (`rf-detr`, `yolo`) servem para qualquer tarefa; imagem de outro perfil só não tem os campos |
| 2026-11 | Label do CVAT = chave do tipo de objeto com caixa; os atributos da caixa são os campos do tipo; label sem tipo fica com os atributos crus | o perfil já dizia isso; sem mapa extra para manter |
| 2026-11 | O reimport do CVAT sobrescreve os atributos editados no SIDM (o ensaio avisa) | o CVAT é a fonte das caixas; casar caixa a caixa seria frágil |
| 2026-11 | Atributo obrigatório de caixa faltando não bloqueia a verificação da imagem | as caixas são por tarefa, com ciclo próprio |
| 2026-11 | Campo de objeto no export/pasta/nome é `<tipo>_<campo>` (do primeiro objeto do tipo); o nome sem o tipo (`plate`) fica como atalho | no `veiculos` os nomes de sempre (`vehicle_type`, `plate_type`) continuam valendo |
| 2026-11 | Export de **várias tarefas** (`tasks`), com as caixas juntas na imagem; `all_tasks` (só as anotadas em todas) é opção, marcada pela tela ao escolher a segunda tarefa; a mesma label em duas tarefas vira uma classe | datasets como para-brisa + placa; sem `all_tasks`, o objeto não marcado viraria fundo |
| 2026-11 | **Pesquisa/dashboard** de imagens fica no módulo `images` (rota de contagem + `memory.go`) e numa tela própria (`/pesquisa`); o export sem labels fica no `exports` e na tela de Exportar. Quem precisar mexer no módulo do outro avisa antes | as duas frentes andam em paralelo sem se chocar nos mesmos arquivos |
| 2026-11 | O `images.ImageFilter` (e o `images.Service.List`) **só cresce**: pode ganhar campos novos (ex.: `Packages []string`), mas nenhum campo existente muda de nome ou de sentido | o export e a pesquisa dependem do mesmo filtro |
| 2026-11 | Um formato de filtro só: `fields.<campo>` e `objects.<campo>`, com os valores no tipo do perfil; nada de formato novo na pesquisa nem no export | "exportar o que eu pesquisei" vira passar os mesmos filtros |
| 2026-11 | Imagens de um perfil de anotação = imagens dos pacotes que usam o perfil (`catalog.PackagesWithProfile`); a pesquisa é sempre de **um perfil** por vez | o perfil é do pacote, não da imagem; misturar perfis (rosto e carro) não faz sentido |
| 2026-11 | A pesquisa conta só as **verificadas** por padrão; pendentes só como opção explícita (igual ao export) | rascunho pode estar incompleto |
| 2026-11 | Arquivos compartilhados (`services/api.ts`, `router.tsx`/menu, `openapi.yaml`, `README.md`, `contexto/`): cada um edita a seção do seu módulo e **adiciona** linhas, sem reescrever as do outro | é onde o merge dá conflito |
| 2026-11 | Uma branch por frente, saindo da `main` atualizada (a `feat/filter` entra antes); quem termina primeiro faz o merge, o outro faz rebase | evita juntar duas frentes grandes de uma vez |
| 2026-11 | `ImageFilter.Packages` (a imagem está em um destes pacotes; vazio = sem filtro; com `Package`, valem os dois) | a pesquisa busca os pacotes de um perfil de uma vez; o export pode usar no lugar do laço por pacote |
| 2026-11 | Pesquisa: `GET /images/stats?profile=` conta por valor só os campos `choice`, `multi` e `bool`; os tipos de objeto **com caixa** ficam de fora (as caixas moram no `boxes`); o filtro de objeto é `objects.<tipo>.<campo>` (o tipo explícito, como os `filters.objects` do export) | contar texto livre ou número por valor não diz nada; sem o tipo, "cor" de dois tipos se misturaria |
| 2026-11 | Labels na pesquisa: `GET /boxes/stats` (no `boxes`) conta as caixas por tarefa e label nas imagens da pesquisa; quem filtra é o `images` (`SearchIDs`, com os mesmos parâmetros do `GET /images/stats`) | o `boxes` já depende do `images`; o contrário faria um ciclo. O filtro mora num lugar só |
| 2026-11 | `platform.ErrInvalid`: erro de módulo que embrulha ele vira 400 em outro módulo | o `boxes` trata o pedido inválido do `images` sem importar ele |
| 2026-11 | Na pesquisa, `package` e `task` repetidos escolhem vários (sem nenhum: todos); o "Não informado" (`missing`) vem pronto do backend | num campo `multi` a conta "total − soma" não funciona |
| 2026-11 | Visual novo: tema escuro quente (referências do Nathan), Figtree + Inter Tight, navbar transparente à direita; cores só por tokens (`styles/theme.css`); refeito por partes: a base geral primeiro, depois tela por tela | o front estava com ~140 tons soltos; um lugar só para as cores deixa as telas consistentes |
| 2026-11 | Tema claro além do escuro, pelos mesmos tokens (`[data-theme='light']`); botão no header alterna claro/escuro, a escolha fica no navegador e, sem ela, vale o tema do sistema | ambientes claros (escritório, sol) pedem o claro; os tokens já centralizavam as cores |
| 2026-11 | Versionamento **dentro do SIDM** (módulo `versions`): um **dataset** é uma pesquisa salva (perfil, pacotes, filtros, tarefas); uma **versão** congela as **verificadas** que passam, com a anotação (campos, objetos, caixas por tarefa), quem, quando, mensagem e o resumo para o dashboard. As imagens não são copiadas | as imagens já são imutáveis (`<sha1>.ext`); o que muda é a anotação. A versão de um pacote é só um dataset com um pacote |
| 2026-11 | Uma versão **nunca muda**; corrigir gera a próxima; dataset com versões não é apagado (**substituída por** 2026-11-24, só a parte do apagar) | um modelo treinado com a v3 tem que sempre apontar para os mesmos dados |
| 2026-11 | DVC **não** entra no SIDM (a verdade é o Mongo + o disco); fica para o lado do treino, versionando o zip exportado de uma versão | duas fontes da verdade para sincronizar seria pior |
| 2026-11 | O resumo da versão é contado na criação com as mesmas funções da Pesquisa (`images.CountStats`, `boxes.CountLabels`); `ImageFilter.IDs` para ler as imagens por sha1 | o dashboard de uma versão antiga abre sem recalcular, e conta igual à Pesquisa |
| 2026-11 | Data e hora do import **sem formato fixo** (`importer.ParseDateTime`): data, hora e ms em partes (`column` + `time_column` + `ms_column`), formatos comuns reconhecidos, dia antes do mês (`date_order: "mdy"` inverte), vários valores = o primeiro, de 2000 até amanhã. O `date_format` antigo é tentado primeiro | o layout exato descartava a data por um detalhe (`10:03:24;10:03:24`, ms com 2 dígitos); uma convenção fixa é previsível |
| 2026-11 | Export sem caixas é um **formato** (`images`), não uma opção dos outros: sem tarefa nem labels (o `Normalize` limpa), as pastas pelos metadados valem também nele, com um grupo só (100/0/0) as imagens vão para a raiz, e o zip leva um `anotacoes.csv` (UTF-8 com BOM e `;`, valores guardados, colunas do `MetaFields` sem os atalhos) | a anotação já está no nome; COCO/YOLO/VOC vazios só gerariam arquivos inúteis, e o CSV abre direto no Excel em português |
| 2026-11 | Dataset **com versões pode ser apagado**, de propósito (`DELETE /datasets/{name}?versoes=apagar`, digitando o nome na tela): somem a pesquisa salva, as versões e os itens congelados. As imagens, a anotação e as caixas não mudam. Sem o `?versoes=apagar`, continua 409 | o dataset é fácil de recriar; quem apaga aceita perder o histórico. Uma versão continua sem ser editada |
| 2026-11 | **Baixar uma versão** = o mesmo `POST /exports/download` (e `/exports/preview`) com `"version": {"dataset", "number"}` (0 = o estado atual). Do perfil de export valem formato, divisão, pastas, nomes e labels; as imagens, os campos e as caixas são os **congelados** na versão (os pacotes e filtros do perfil não valem). O zip sai `<dataset>-v<n>-<perfil>.zip` e o `export_info.json` diz a versão (dataset, número, id) | reaproveita o formato do export (um zip só para manter) e o modelo treinado aponta para dados que não mudam |
| 2026-11 | Perfil de import **padrão** `splice-ini` no código (`importer.Builtins`), como os padrões de export: não fica no banco, aparece primeiro na lista, não se cria/edita/renomeia/apaga com o mesmo nome; um salvo antes com o nome dele fica escondido. Data/hora do `[Metrologico]` em partes, equipamento do `NSerie`, tipo pelo `TipoVeiculo` com map Denatran → veiculos. O upload busca o perfil por `imports.Profiles` (padrão primeiro). Na tela, como nos perfis de anotação: Ver (só leitura) e Duplicar; o editor grava a data em partes (`time_column`/`ms_column`, formato automático por padrão) em vez do template | vem pronto em toda instalação, igual para todos, e não quebra por uma edição na tela |
| 2026-11 | **Login no mesmo Mongo** (módulo `users`, coleções `users` e `sessions`), não um banco novo. Cadastro fica **pendente** até um admin aprovar; sessão de **8 h** em cookie HttpOnly/SameSite=Lax, com só o sha256 do token no banco (TTL apaga). Senha em PBKDF2-SHA256 da biblioteca padrão (600 mil iterações), sem dependência nova. O primeiro admin vem do `.env` (`SIDM_ADMIN_USER`/`SIDM_ADMIN_PASSWORD`) só quando não há admin ativo. 5 senhas erradas seguidas = 5 min de espera | um banco a mais é mais backup e configuração sem ganho; o histórico continua com o nome de login (o `X-User` passa a vir da sessão) |
| 2026-11 | (**substituída por** 2026-11-24, a seguinte) **Só admin:** apagar qualquer coisa (todo `DELETE`), gravar perfis de anotação e de import (Configurar) e gerenciar contas. Usuário normal anota, importa, exporta, cadastra equipamento/câmera na anotação e cria datasets e versões. A tela esconde o que a pessoa não pode, mas quem garante é o backend | o que não se desfaz fica com quem responde pelo sistema |
| 2026-11 | **Entrar pelo e-mail.** O cadastro pede nome, e-mail e senha; o nome de usuário (o do histórico das imagens) sai do e-mail (`maria.silva@...` → `maria.silva`, `-2` se já existe). E-mail único (índice parcial: o admin do `.env` pode não ter). O login aceita o e-mail ou o nome de usuário | as pessoas lembram o e-mail; o histórico continua com um nome curto e estável |
| 2026-11 | **Usuário normal grava só o que está na lista** (`userWrites` em users/http.go): anotar, importar (pacote novo, upload, CSV, caixas do CVAT), apagar imagens, baixar o export, criar datasets e versões. Todo o resto que grava é admin: tarefas e labels (nome, descrição, cores), perfis de anotação/import/export, renomear e apagar pacotes, apagar datasets, cadastros e contas | lista do que pode (e não do que não pode): uma rota nova nasce só de admin até alguém decidir |
| 2026-11 | **Lixeira + volta pela versão.** Apagar uma imagem não apaga mais o arquivo: o registro inteiro vai para `images_trash` e o arquivo para `lixeira/<sha1>.ext` (as caixas saem, o histórico fica). No "O que mudou", uma imagem volta para como estava na versão (`POST .../versions/{n}/items/{sha1}/restore`): campos, objetos e caixas da versão; se foi apagada, sai da lixeira. A volta passa pelo perfil do pacote (como uma anotação) e fica no histórico ("via volta para a vN"). Usuário normal pode apagar imagens e voltar | as versões só guardam a anotação; sem lixeira, uma imagem apagada não teria como voltar. A lixeira cresce: limpar fica para depois |
| 2026-11 | **Voltar tudo para a versão (só admin):** `POST /datasets/{name}/versions/{n}/restore` volta as alteradas e as que saíram desde a vN (as apagadas saem da lixeira); as que entraram depois ficam. Uma que falha não para as outras (relatório). Segue até o fim mesmo se o navegador fechar. Na tela, pede para digitar `vN` | desfazer uma mudança errada em milhares de imagens de uma vez; quem não é admin volta uma por uma |
| 2026-11 | **Herança de perfis de anotação** (`extends`): um perfil (ex.: `moto`) estende outro (`veiculos`) e tem os campos e tipos de objeto dele, mais os seus. No banco, cada perfil guarda só o que é dele; a API devolve o perfil **resolvido** (o herdado com `from`, mais `lineage`). O filho só **acrescenta**: chave repetida é erro; um tipo do pai pode ser repetido só para ganhar campos e caixas. Até 5 níveis, sem círculo. Um pai com filhos não se apaga, e mudar o pai confere se os filhos continuam fechando. Datasets, pesquisa e stats de um perfil incluem os pacotes dos que o estendem | um pacote tem um perfil só (consultas simples), e mesmo assim motos e caminhões entram juntos num dataset de veículos |
| 2026-11 | **Caixa ligada a um objeto**: um tipo de lista (ex.: veículo) diz quais labels de caixa o representam (`box_labels`, com o que cada label já diz: `motorcycle` → `type = motorcycle`). Na anotação, o objeto guarda a caixa (`box`: tarefa, label e posição, porque as caixas não têm id fixo; a tela acha de novo pela posição, ou pela mais parecida, IoU ≥ 0,5). O backend preenche o que a label diz e recusa valor diferente; uma caixa não é de dois objetos. A tela trava os campos que vêm da caixa e oferece "+ Veículo desta caixa" para as caixas soltas | a caixa motorcycle e o Veículo 1 são a mesma coisa na imagem; ligar evita anotar o tipo duas vezes e deixa o treino cruzar caixa e placa |
| 2026-11 | **Perfil padrão com caixas editáveis**: de um padrão (ex.: `veiculos`), só as `box_labels` de cada tipo mudam (`PUT` normal; o resto que vier é ignorado). Ficam no banco num registro com o nome do padrão que só tem os tipos e as caixas (`annotation/tuning.go`); a lista não mostra esse registro como outro perfil. Mudar confere os filhos (ex.: `moto` não pode já ter a mesma label). Só admin, como o resto do Configurar | labels novas aparecem com tarefas novas no CVAT; ligar uma label a um tipo não muda o que já foi anotado, então não precisa duplicar o padrão |
